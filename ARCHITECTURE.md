# Архитектура Copmuter

Документ описывает новую реализацию: **C++ ядро + Python-мозг + C# оболочка**.
Прежняя Python-реализация (`agent/`) сохранена как справочник и здесь не описана.

---

## 1. Слои и ответственность

| Слой | Где | Что делает | Чего не делает |
|---|---|---|---|
| Оболочка | `shell/Copmuter.Agent` (C# + WinUI 3) | окно, чат, статусы, настройки, PLAN ONLY, «Стоп», надзор за процессами | не вызывает Win32, не работает с файлами и вводом |
| Ядро | `native/` (C++20, `AgentRuntime.dll`) | маршрутизация, разбор фраз, реестр приложений, оптимизатор, инструменты, проверка, восстановление, ожидания, IPC-сервер | не рассуждает и не сочиняет план |
| Мозг | `ai/` (Python, постоянный воркер) | планирование, рассуждение, код, зрение, контекст, память (SQLite) | не выполняет системных действий сам |

Ядро и воркер — **постоянные процессы**. Ни Python, ни модель не поднимаются на
каждую команду: воркер стартует вместе с приложением, соединение с LM Studio тёплое,
канал C++ ↔ Python открыт всю сессию.

Принцип: **LLM — мозг, C++ Runtime — руки, Vision — глаза, Router — рефлексы,
Verification — контроль результата.**

## 2. Три пути выполнения

```
                       ┌──────────────────────────────────────────────┐
ПОЛЬЗОВАТЕЛЬ → ROUTER ─┤ 1. DIRECT  инструмент ядра (WinAPI/Shell/CLI)│→ ПРОВЕРКА → РЕЗУЛЬТАТ
   (C++, ~11 мкс)      ├ 2. AGENT   Python/Qwen3-VL → план → инструм. │→ проверка → переплан
                       └ 3. VISION  снимок → Qwen3-VL → координаты    │→ ввод ядра → проверка
```

1. **Direct** — всё, что можно сделать детерминированно: запуск приложения, ссылка,
   файлы, папки, громкость, обои, питание, папки-места, горячие клавиши, поиск в
   интернете, скриншот, переключение окна. Модель не вызывается.
2. **Agent** — задачи, где нужен план: «напиши калькулятор на Python», «разберись,
   почему тормозит». Мозг возвращает вызовы инструментов, ядро их исполняет и
   возвращает наблюдения; цикл повторяется до `finished` или до лимита шагов.
3. **Vision** — когда детерминированного пути нет: неизвестный интерфейс, «нажми
   кнопку Y». Снимок → модель зрения → координаты (нормализованные 0..1000) →
   масштабирование в экранные → клик ядра → проверка по изменению экрана.

## 3. Модули ядра (`native/src`)

| Файл | Ответственность |
|---|---|
| `core_intent.cpp`, `core_intent_parse.cpp` | нормализация, стемминг, глаголы и объекты, места («рабочий стол», «загрузки»), составные команды, сложные задачи, заученные формулировки |
| `core_router.cpp` | выбор маршрута и обоснование («детерминированный инструмент» / «несколько простых действий» / «нужна модель») |
| `core_registry.cpp` | реестр инструментов: имена, описания, параметры, категория, риск, предпочтительный способ, таймаут, проверка результата, запасные способы, GUI-флаг |
| `core_optimizer.cpp` | лестница способов и обучение: WinAPI → кеш exe → CLI → Shell → ярлык → UIA → ввод → зрение → LLM, со статистикой по каждой паре (инструмент, способ) |
| `core_batch.cpp` | пакеты действий: последовательно, параллельно, с зависимостями, остановкой по ошибке и проверкой |
| `core_execute.cpp` | исполнение намерений: запуск приложений с бюджетом и повторами, фокус окна, ссылки, папки, файлы, поиск, питание, ввод, оболочка |
| `core_wait.cpp` | ожидания по состоянию: процесс, окно, файл, порт, условие; адаптивный шаг опроса, отмена |
| `core_tool_call.cpp` | один вызов инструмента от мозга → JSON-наблюдение (`run_tool`) |
| `core_agent_loop.cpp` | агентный цикл: план → исполнение → наблюдения → переплан; защита от циклов и ложного успеха |
| `core_runtime.cpp` | жизненный цикл, конфиг, события, метрики, `verify_action`, подтверждения |
| `core_util.cpp` | разбор JSON-аргументов (включая `\uXXXX`), маленькие парсеры |
| `platform_win32.cpp` | настоящее Windows: процессы (Toolhelp), окна, SendInput, буфер, файлы, корзина, ShellExecute, реестр/App Paths/протоколы/UWP, DXGI-снимки, обои, громкость (Core Audio), настройки |
| `platform_linux.cpp` | dev-реализация с честными отказами (нужна, чтобы ядро логики тестировалось без Windows) |
| `core_png.cpp` | глаза: уменьшение кадра, PNG для модели (GDI+ на Windows, свой писатель на Linux), сравнение кадров (0..1), base64 |
| `ipc_posix.cpp`, `ipc_win32.cpp` | канал к мозгу: Unix-сокет / Named Pipe, кадры «длина + JSON» |

| `host_main.cpp` | `agent_host` — запуск ядра без UI |

## 4. C ABI (`native/include/agent/runtime.h`)

```c
int32_t  agent_init(const char* config_json);      // 0 | 10 (конфиг) | 11 (старт)
void     agent_shutdown();
char*    agent_execute(const char* phrase);        // быстрый путь
char*    agent_preview(const char* phrase);        // PLAN ONLY
char*    agent_run_task(const char* task, int max_steps);   // полный проход (fast | agent)
char*    agent_run_tool(const char* tool, const char* args_json);
char*    agent_metrics_json(); char* agent_state_json(); char* agent_tools_json();
void     agent_set_event_sink(void (*fn)(const char*, void*), void* user);
void     agent_cancel_current();                   // «Стоп» на уровне исполнителя
const char* agent_last_error();

```

Конфиг — JSON: `state_dir`, `safety_mode`, `default_browser`, `language`, `preload`,
`launch_timeout_ms`, `file_timeout_ms`, `browser_timeout_ms`, `window_timeout_ms`,
`process_timeout_ms`, `shell_timeout_ms`, `vision_timeout_ms`, `max_retries`,
`screenshot_max_pixels`, `ai_socket`, `llm_timeout_ms`, `max_steps`, `dry_run`.

## 5. Канал C++ ↔ Python

* Транспорт: **Named Pipe** `\\.\pipe\agent_ai_v1` (Windows), Unix-сокет в dev.
* Кадр: `[uint32 BE длина][UTF-8 JSON]`, один запрос — один ответ, до 64 МиБ.
* Запросы: `plan`, `replan`, `chat`, `code`, `vision`, `compress`, `preflight`, `health`.
* План-ответ: `{"id","ok","kind":"plan","say","calls":[{"tool","args","note"}],"finished"}`.
* Ошибки: `{"id","ok":false,"error":"человеческая причина"}` — канал при этом не рвётся.
* Кто кого запускает: оболочка поднимает Python-воркер и следит за ним, ядро
  подключается к каналу. Обрыв канала — не повод перезапускать воркер на каждую
  команду: соединение переиспользуется.

## 5.1. Сложные страницы: Playwright

Прямые ссылки (поиск, YouTube, открытие сайта) открывает нативное ядро — это миллисекунды,
и Playwright туда не подключается. Playwright нужен там, где страница требует
взаимодействия: заполнить форму, дождаться SPA, вытащить данные, скачать файл.

* Инструмент `browser_task` (`action`: open/click/fill/press/text/links/html/eval/wait/
  screenshot/download/back/info) уходит запросом `browser` по тому же каналу.
* Python держит **один** Chromium на сессию (`ai/browser.py`): запуск браузера на каждое
  действие — секунды, которых в бюджете нет. Селекторы понимают CSS, `text=…`,
  `role=button[name=…]`, XPath.
* Ожидания — по состоянию (селектор, URL, `networkidle`), а не `sleep`.
* Если Playwright/Chromium не установлены, пользователь получает инструкцию, а не трейсбек;
  ядро при этом продолжает работать остальными путями.

## 5.2. Путь зрения

`нажми кнопку X` (или `click_element`) роутер отправляет по пути зрения — без круга
планирования, потому что модель здесь нужна как глаза, а не как мозг:

1. ядро снимает кадр (всей области или `region`/`monitor`), уменьшает и кодирует в PNG;
2. Python-воркер отдаёт кадр Qwen3-VL и получает координаты в нормализованном 0..1000;
3. координаты переводятся в экранные (учитывая смещение области и DPI) и кликает **ядро**
   через SendInput;
4. ядро снимает кадр после клика и сравнивает его с прежним: если экран не изменился,
   это честно сообщается — «нажал, но реакции нет», а не «готово».

## 6. Контракт инструмента и лестница способов

Каждый инструмент описывается именем, описанием, параметрами (JSON Schema), категорией,
риском (`None/Low/Medium/High/Critical`), предпочтительным способом, таймаутом,
проверкой результата, списком запасных способов и флагом GUI.

Порядок способов задаёт Execution Optimizer: **WinAPI → кешированный exe → CLI/API →
Shell → ярлык → UI Automation → ввод/зрение → полный агентный цикл.** Реальный порядок
уточняется статистикой: успешные пары поднимаются, провальные опускаются.

Проверка результата: запустился ли процесс, появилось ли окно, стал ли активным,
существует ли файл, ушёл ли файл, изменился ли файл/экран, загрузился ли URL, открылся
ли порт, нулевой ли код возврата.

## 7. Ожидания и таймауты

Никаких `sleep(1/3/5)` как способа синхронизации. `WaitManager` опрашивает **состояние**
с адаптивным шагом (2 → 25 → 100 → 250 мс) и умеет отменяться по «Стоп».

Бюджеты по умолчанию: запуск 12 с, файлы 5 с, браузер 15 с, окно 8 с, процессы 10 с,
оболочка 60 с, зрение 20 с. Таймаут конкретного действия (`ActionSpec.timeout_ms`)
перекрывает бюджет и ограничивает **каждую** попытку, чтобы отказ не «съедал» полный
таймаут на каждый способ.

## 8. Контекст и память

Context Manager собирает для модели: компактный системный промпт + **только
релевантные инструменты** (ядро + упоминания в задаче + явно запрошенные; пол 12,
потолок 24) + сжатое состояние ПК + окно истории + задача и наблюдения шага. Бюджет
считается до вызова модели, история подрезается, при перерастании — сжимается резюме.

Память — SQLite (`ai/memory.py`): чаты и сообщения, задачи и их результат, история
вызовов инструментов, обученные пути приложений, факты о пользователе, метрики,
настройки. Ядро держит быстрый кеш реестра приложений (TSV/JSON) и файл подтверждённых
путей.

## 8.1. Подтверждение опасных действий (конец-в-конец)

Опасное действие (массовое удаление, критические настройки, выключение, риск `critical`)
ядро не выполняет молча — оно **останавливается и спрашивает**. Механика одна и та же
для оболочки и для терминала:

1. `needs_confirmation()` в ядре решает, нужен ли вопрос (режим безопасности + риск + охват).
2. Ядро публикует событие `confirm/pending` с понятным вопросом (что именно и почему) и
   **ждёт ответа** `confirm_timeout_ms` (настраивается; оболочка ставит 30 с).
3. Оболочка ловит событие и показывает диалог (кнопка по умолчанию — «Отмена», чтобы Enter
   не удалял); `agent_host --confirm` спрашивает в терминале. Ответ уходит обратно через
   `agent_answer_confirmation(1|0)` (P/Invoke) или `AgentRuntime::set_confirm_handler()`.
4. Молчание (нет ответа, никто не слушает, таймаут) — это **отказ**: действие не
   выполняется, пользователю объясняется причина. Значение по умолчанию — безопасное.
5. Результат подтверждения отражается событием `confirm/approved|denied`, поэтому в UI
   видно, что произошло.

Проверяется тестами: согласие → действие выполнено и проверено; отказ → объект на месте;
молчание → объекта тоже не касаются; обработчик UI отвечает мгновенно, ожидания нет.

## 9. Метрики

`agent_metrics_json()` и таблица метрик воркера: время маршрутизации, число вызовов
модели, число вызовов инструментов, провалы и откаты, доля успеха, среднее время
способа. Главная метрика — **Time To Completion** (от фразы пользователя до
проверенного результата).

## 11. Тестирование

* **Сценарии ТЗ (59 проверок)** — `native/build/agent_scenarios`: все 10 обязательных
  сценариев на подменённой платформе. Печатает итог и код возврата, годится для CI.
* **Ядро (158 тестов)**: разбор и маршрутизация, реестр и оптимизатор, пакеты, ожидания,
  полный цикл простых команд, **агентный цикл через настоящий Python-воркер**,
  честность отказов (неудачный запуск не выдаётся за успех), подтверждение опасных
  действий, ABI, IPC, бенчмарк маршрутизатора.
* **Windows-сборка без Windows**: `native/build_windows_cross.sh` (zig, `x86_64-windows-gnu`)
  компилирует все Windows-исходники, линкует `AgentRuntime.dll` + `agent_host.exe` и
  сверяет экспорты DLL с C ABI в `runtime.h`. Это ловит ошибки, которые иначе видны
  только на машине пользователя: рукописные COM-vtable, забытый `__declspec(dllexport)`,
  несуществующий `.def`, несовпадение списка функций для C#.
* **Мозг (43 теста)**: план и разбор вызовов инструментов (function calling и JSON
  текстом), защита от повторов, бюджет контекста, память, зрение и координаты
  (доли/пиксели/0..1000), протокол и сервер воркера.
* Сценарии без модели: `ai/fake_brain.py` и `ai/dev_scripted.py` — тест поднимает их
  как отдельный процесс, ядро реально создаёт файлы, содержимое проверяется на диске.

## 12. Осознанные решения

* **Почему ядро на C++**: миллисекунды на старте приложения, SendInput, реестр, окна и
  DXGI-снимки — это то, что определяет отзывчивость. Python-стек таких задержек не даёт.
* **Почему Python всё равно нужен**: экосистема моделей, зрение, код, простая отладка
  промптов. Мозг и руки разделены, поэтому каждый слой развивается независимо.
* **Почему не gRPC между C# и C++**: для внутрипроцессной связи достаточно P/Invoke;
  лишний транспорт — лишняя задержка и лишние сбои.
* **Почему модель не управляет каждым шагом**: простые действия должны занимать
  миллисекунды. Модель подключается там, где нужен план или зрение.
* **Честность вместо «успеха»**: если команды нет, ссылка не открылась или окно не
  появилось, пользователь видит причину, а не выдуманный результат.
