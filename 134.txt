# MASTER PROMPT — TRANSFORM THE EXISTING AI COMPUTER AGENT INTO A PRODUCTION-GRADE COMMERCIAL DESKTOP PRODUCT

## 0. ТВОЯ ЗАДАЧА

Ты работаешь над существующим проектом **AI Computer Agent**.

Это НЕ новый проект с нуля и НЕ небольшое приложение.

Существующий код — это ранний прототип с большим количеством уже реализованной функциональности, но с серьёзными архитектурными, производительными, UX, AI, security и reliability проблемами.

Твоя задача:

> **Превратить существующий прототип в полноценный коммерческий desktop-продукт production-grade качества.**

Итоговый продукт должен ощущаться не как Python-проект, не как эксперимент и не как AI-generated dashboard, а как приложение, которое потенциально можно продавать миллионам пользователей.

Текущая реализация является лишь исходным материалом.

**Не защищай существующую архитектуру.**

Если архитектура плохая — перепиши её.

Если язык не подходит — замени.

Если библиотека плохая — замени.

Если subsystem проще и быстрее реализовать нативно — реализуй нативно.

Если функциональность проще сделать deterministic code — не используй LLM.

Если существующий код мешает качеству — удаляй его.

Главный объект оптимизации:

> **не текущий код, а конечный продукт.**

# 1. ИСХОДНЫЙ ПРОДУКТ

Концепция приложения:

Пользователь говорит агенту, **какой результат хочет получить**, а агент самостоятельно:

1. понимает цель;
2. определяет необходимые действия;
3. строит план;
4. выбирает инструменты;
5. выполняет действия;
6. наблюдает результаты;
7. проверяет, достигнута ли цель;
8. исправляет ошибки;
9. меняет стратегию при необходимости;
10. завершает задачу только после фактической проверки результата.

Компьютер является единой средой выполнения:

* файловая система;
* процессы;
* окна;
* приложения;
* браузер;
* терминал;
* PowerShell;
* экран;
* мышь;
* клавиатура;
* clipboard;
* ОС;
* Git;
* сеть;
* настройки;
* AI models;
* voice;
* память;
* расписание;
* фоновые задачи.

Уже существующий проект содержит значительную часть этой функциональности.

**Не потеряй её при рефакторинге.**

# 3. АГЕНТ ДОЛЖЕН САМОСТОЯТЕЛЬНО ВЫБИРАТЬ СПОСОБ РЕШЕНИЯ

Это обязательное требование.

Пользователь задаёт **цель**, а не implementation plan.

Например:

> "Открой Chrome"

Агент НЕ должен:

```text
LLM request
→ tool selection
→ generated PowerShell
→ PowerShell
```

если можно сделать:

```text
native Windows Shell API
→ Chrome
```

почти мгновенно.

Другие примеры:

### Создать директорию

Filesystem API.

### Найти процесс

Native OS API.

### Получить размер папки

Filesystem/native API.

### Открыть URL

Native shell/browser API.

### Запустить программу

Native process launch.

### Найти текст в файлах

Fast filesystem/search engine.

### Выполнить сложный shell workflow

PowerShell / CLI.

### Управлять браузером

Playwright/browser automation.

### Найти кнопку в неизвестном UI

Accessibility tree → OCR → Vision как fallback.

### Понять неоднозначную пользовательскую задачу

LLM.

# 4. АГЕНТ ИМЕЕТ ПРАВО НЕ СЛЕДОВАТЬ ПОЛЬЗОВАТЕЛЬСКОМУ СПОСОБУ

Если пользователь говорит:

> "Сделай X через Y"

агент должен оценить, действительно ли Y является оптимальным способом.

Если существует существенно более быстрый/надёжный способ — агент может использовать его.

Если пользователь говорит:

> "Открой Chrome через PowerShell"

а native API быстрее и безопаснее, агент может использовать native API, если нет причины строго соблюдать PowerShell.

При необходимости агент может объяснить:

> "Я использовал системный API вместо PowerShell, потому что это быстрее и надёжнее."

# 6. ТЕХНОЛОГИЧЕСКАЯ СТРАТЕГИЯ

## Не считать Python обязательным.

Текущий Python-код существует потому, что это был прототип.

Это НЕ означает, что production-продукт должен остаться Python-приложением.

Проведи анализ каждого слоя:

### Desktop shell

Оцени native Windows / Rust / C++ / C# / Qt / Tauri / WebView / другие подходы.

### Agent runtime

Оцени Rust / C++ / Python / hybrid architecture.

### UI

Оцени современные desktop UI технологии.

### OS integration

Предпочитай native APIs.

### AI providers

Используй отдельный abstraction layer.

### Browser

Используй зрелый browser automation engine.

### Storage

Используй подходящее локальное хранилище, а не хаотичный набор JSON-файлов.

### IPC

Используй нормальный IPC между компонентами, если архитектура multi-process.

**НЕ ПЫТАЙСЯ СДЕЛАТЬ ХОРОШИМ СУЩЕСТВУЮЩИЙ ПРОТОТИП.**

Сделай хороший продукт.

Если нужно оставить часть Python — оставь.

Если нужен C++ — используй C++.

Если LLM не нужен — не используй его.

Если нужен Vision — используй Vision.

Если Vision не нужен — не используй его.

Если существующая архитектура мешает — уничтожь её и построи нормальную.

**Ты отвечаешь не за сохранение существующего кода.**

Ты отвечаешь за то, чтобы на выходе получился:

> **быстрый, красивый, надёжный, безопасный, интеллектуальный, расширяемый и коммерчески готовый AI Computer Agent для desktop.**

* mmap where appropriate;
* incremental processing.

Не загружать гигантский файл целиком в RAM без необходимости.

---

# 196. TEMPORARY FILE MANAGEMENT

Все temp files:

* уникальные;
* tracked;
* cleaned;
* recoverable where required.

После crash должен существовать cleanup/recovery mechanism.

---

# 197. FILE LOCK HANDLING

Корректно обрабатывать:

* file in use;
* permissions;
* network drive;
* OneDrive/Dropbox syncing;
* antivirus locks.

Не считать файл отсутствующим только потому, что он временно locked.

---

# 198. CLOUD-SYNC AWARENESS

Если файл находится в:

* OneDrive;
* Dropbox;
* Google Drive;

учитывать:

* online/offline;
* sync status;
* placeholders.

# 199. NETWORK DRIVE SUPPORT

Filesystem tools должны корректно работать с UNC/network paths там, где это поддерживается.

---

# 200. PATH NORMALIZATION

Корректно работать с:

* Unicode;
* spaces;
* long paths;
* UNC;
* symlinks;
* junctions.

---

# 201. WINDOWS LONG PATHS

Поддержать long paths, если OS/configuration позволяет.

# 202. PROCESS SECURITY

Перед kill/modify process:

* проверить identity;
* PID;
* executable;
* permissions.

# 203. RACE CONDITION PROTECTION

---

# 297. FINAL PRINCIPLE

**Если можешь сделать операцию за 1 ms без AI — не делай её за 2 секунды через AI.**

**Если можешь получить точный state через API — не угадывай его через Vision.**

**Если можешь проверить результат программно — не спрашивай LLM, получилось ли.**

**Если можно выполнить действия параллельно — не выполняй их последовательно.**

**Если можно избежать network request — избегай его.**

**Если можно избежать запуска тяжёлого subsystem — не запускай его.**

**Если можно обнаружить ошибку автоматически — обнаруживай её автоматически.**

**Если можно восстановиться автоматически — восстанавливайся автоматически.**

---

# 298. FINAL ENGINEERING STANDARD

Secure

+
Maintainable
